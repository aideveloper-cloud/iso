# ISO 9001 Document Control — v2 (Svelte + Tailwind + Bun + Rust + Go + PostgreSQL)

ระบบควบคุมเอกสาร ISO 9001:2015 ของบริษัท เค การ์เด้น แอนด์ เฟนซ์ จำกัด

## สถาปัตยกรรม
```
Svelte + Tailwind + Bun  (frontend, :5173)  ──►  Rust API (Axum, :8085)  ──►  PostgreSQL (:5432, Docker)
        │                                              │
        └───────────── ผ่าน Vite proxy ───────────────┴──►  Go converter (:8081)  (docx → HTML)
```
- **Svelte + Tailwind CSS + Bun** — หน้าเว็บ (Vite dev server รันด้วย Bun); สไตล์ทั้งหมดใช้ Tailwind (ธีม/สีอยู่ใน `frontend/tailwind.config.js`)
- **Rust (Axum)** — API หลัก: `/api/docs`, `/api/stats`, `/api/overview`, `/api/actions` (CAR/DAR/PAR), เวอร์ชัน+ลายเซ็นเก็บใน **PostgreSQL** (`/api/health` เช็ค DB + Go)
- **PostgreSQL** — ตาราง `versions` เก็บประวัติเวอร์ชัน + ลายเซ็นผู้แก้ไข (รันผ่าน Docker Compose)
- **Go** — บริการแปลงเอกสาร: `/health`, `/convert` (docx → HTML)

## วิธีรัน
**ดับเบิลคลิก `start-all.bat`** — เริ่ม PostgreSQL (Docker) + 3 บริการ แล้วเปิดเบราว์เซอร์ที่ http://localhost:5173

### ใช้ในวง LAN
Frontend เปิดรับจากทุก interface (`--host`) — เครื่องอื่นใน Wi‑Fi/LAN เดียวกันเข้าได้ที่:
`http://<IP-เครื่องเซิร์ฟเวอร์>:5173`  
(สคริปต์ `start-all.bat` จะพิมพ์ IP ให้ และพยายามเปิด Firewall พอร์ต 5173)  
คำขอ `/api` ถูก proxy ผ่าน Vite ไปยัง API บนเครื่องเซิร์ฟเวอร์ ไม่ต้องเปิดพอร์ต 8085 ให้ LAN

หรือรันแยกเอง:
```bash
# 0) PostgreSQL (Docker Desktop ต้องเปิดอยู่)
docker compose up -d
# 1) Go converter
cd converter && go run .
# 2) Rust API  (DATABASE_URL ชี้ไป Postgres ของ docker-compose)
cd api && DATABASE_URL="host=localhost port=5432 user=iso password=iso dbname=iso" cargo run
# 3) Svelte + Bun
cd frontend && bun install && bun run dev
```

### PostgreSQL / การย้ายข้อมูล
- ตั้งค่า connection ผ่าน env `DATABASE_URL` (ค่าเริ่มต้นตรงกับ `docker-compose.yml`: user/password/db = `iso`)
- ครั้งแรกที่รัน ถ้าตาราง `versions` ใน Postgres ยังว่าง **และ** มีไฟล์ SQLite เดิม (`data/versions.db`) API จะ **migrate ข้อมูลเวอร์ชันเก่าให้อัตโนมัติ** ครั้งเดียว
- หยุด/ลบ DB: `docker compose down` (คง data), `docker compose down -v` (ลบ data ทั้งหมด)

## โปรเจกต์ open source ที่ใกล้เคียง (อ้างอิงแนวทาง UI/workflow)
เนื่องจากไม่มี QMS open source ที่ใช้ stack เดียวกัน (Rust/Svelte) โดยตรง ใช้เป็นแรงบันดาลใจด้าน UX/เวิร์กโฟลว์:
- **Docuseal** (github.com/docusealco/docuseal, Rails+Vue, AGPL) — ตัวอย่าง e-signature/approval flow ที่ดีที่สุด: ลำดับผู้เซ็น, สถานะการอนุมัติ, หน้า audit trail — ตรงกับฟีเจอร์ "ลงชื่อก่อนบันทึกเวอร์ชันใหม่"
- **Mayan EDMS** (github.com/mayan-edms/Mayan-EDMS, Django, Apache-2.0) — DMS ที่ใกล้ ISO ที่สุด: version list + revert, workflow state machine, cabinet/metadata คล้ายการจัดตามแผนก
- **Paperless-ngx** (github.com/paperless-ngx/paperless-ngx, Django+Angular, GPLv3) — UI ทะเบียนเอกสาร/แดชบอร์ด + ตัวอ่าน PDF ที่ทันสมัยและดูแลต่อเนื่อง
- อื่น ๆ: OpenQMS.net (โดเมน ISO 9001 ตรงสุด), LogicalDOC / OpenKM (workflow engine + version history UI)

## การแก้ไขไฟล์บนเว็บ (คงรูปแบบเดิม)
- **Word (.docx)** — `converter/docx.go` แปลงเป็น HTML ที่คงหน้ากระดาษ ตาราง สี เส้นขอบ รูป หัว/ท้ายกระดาษ เลขรายการ แล้วใส่ `data-p / data-tr / data-r` กำกับ; ตอนบันทึก `frontend/src/lib/docxpatch.js` **แก้ไฟล์ .docx ต้นฉบับในที่เดิม** (แตะเฉพาะย่อหน้า/แถวที่เปลี่ยน) ไม่สร้างไฟล์ใหม่ จึงไม่เสียฟอร์ม
- **Excel (.xlsx)** — `lib/xlsxview.js` แสดงตามต้นฉบับ (merge, สี, เส้น, ความกว้าง) และ `lib/xlsxpatch.js` แก้เฉพาะเซลล์ที่เปลี่ยนในไฟล์เดิม (ทดสอบ: `cd frontend && node scripts/test-xlsx.mjs`)
- **.xls (ไบนารีเก่า)** — แก้ในที่เดิมไม่ได้ ใช้ SheetJS อ่าน/เขียนกลับ สีและเส้นขอบบางส่วนอาจหายเมื่อบันทึก
- ข้อจำกัด Word: ตำแหน่งรูป/กล่องข้อความที่ลอยอยู่จะแสดงเป็น inline, ฟอนต์ที่เครื่องไม่มีจะถูกแทนที่, เปลี่ยนจัดชิด/ขนาดตัวอักษรบนเว็บยังไม่รองรับ (มีตัวหนา/เอียง/ขีดเส้นใต้/เพิ่ม-ลบแถว)

## ควบคุมการเปลี่ยนแปลงเอกสาร (DCR — ISO 9001:2015 ข้อ 7.5.2–7.5.3)
เอกสารในทะเบียน (QM/QP/WI/FM) **แก้ไขได้ผ่านคำขอเปลี่ยนแปลงเท่านั้น** (`api/src/doccontrol.rs`, หน้า "คำขอเปลี่ยนแปลงเอกสาร")
1. **ผู้จัดทำ** แก้บนเว็บหรือแนบไฟล์ → ระบุเหตุผล + Rev. ใหม่ (ระบบเสนอให้ เช่น Rev.00 → Rev.01) → ส่ง `DCR-<พ.ศ.>-<ลำดับ>` ฉบับใช้งานเดิมยังใช้ต่อจนกว่าจะอนุมัติ
2. **ผู้ตรวจสอบ** (role `reviewer`/`approver`/`admin`) ผ่าน หรือตีกลับพร้อมเหตุผล → ผู้จัดทำแก้แล้วส่งใหม่
3. **ผู้อนุมัติ** (role `approver`/`admin`) อนุมัติ → สร้างเวอร์ชันใหม่ที่มี Rev. / วันที่บังคับใช้ / ผู้อนุมัติ และซิงก์ไฟล์ต้นฉบับบนดิสก์
- ผู้ลงนามทุกขั้นคือผู้ใช้ที่ login (ไม่มีช่องพิมพ์ชื่อเอง) และต้อง **กรอก PIN ซ้ำ**; ผู้จัดทำตรวจ/อนุมัติคำขอของตนเองไม่ได้ (ยกเว้น admin ตามกติกาเดียวกับ e-form)
- ทุกขั้นบันทึก **SHA-256 ของไฟล์ที่ลงนาม**; ถ้าไฟล์ฉบับร่างถูกแก้หลังลงนาม ระบบไม่ยอมให้อนุมัติ · ทุกการกระทำเข้า `audit_log`
- เอกสารหนึ่งฉบับมีคำขอค้างได้ครั้งละ 1 ใบ · ไฟล์ฉบับร่างเก็บที่ `data/storage/changes/`
- **ยกเลิกใช้ (Obsolete)** โดยผู้อนุมัติ / นำกลับมาใช้โดย admin — ไฟล์ที่ดาวน์โหลดจากเอกสารยกเลิกใช้ขึ้นต้นด้วย `OBSOLETE -` และเวอร์ชันเก่าขึ้นต้นด้วย `UNCONTROLLED vN -`
- เวอร์ชันที่บันทึกก่อนเปิดใช้ DCR แสดงป้าย "ไม่ผ่าน DCR" ในประวัติ; ไฟล์ในคลังภาพรวมที่ไม่อยู่ในทะเบียนยังบันทึกตรงได้ (ผู้ลงนามจากเซสชัน)

## เตรียม Audit — ความพร้อมรับการตรวจ (ต่อยอดจาก AI & Audit Dashboard)
`api/src/readiness.rs` · `GET /api/readiness` คำนวณจากข้อมูลจริงในระบบทุกครั้ง (ไม่มีข้อมูลตัวอย่าง)
- **รายการตรวจระบบ**: ไฟล์ครบ, ฉบับที่ใช้งานผ่าน DCR, นอกทะเบียน/ไฟล์ซ้ำ, DCR ค้าง >14 วัน, CAR/DAR/PAR (เกินกำหนด, ใกล้ครบ 14 วัน, ไม่มีผู้รับผิดชอบ, ปิดโดยไม่มีบันทึก, ยังไม่มีบันทึกเลย), แบบฟอร์มค้างอนุมัติ >7 วัน, บันทึกการอบรม
- **หลักฐานตามข้อกำหนด 4–10**: แผนผังข้อ → รหัสเอกสารอยู่ใน `data/clauses.json` (QMR แก้ได้ แล้วรีสตาร์ต API) — ข้อที่บังคับมีเอกสารแต่ไม่มีฉบับใช้งาน = วิกฤต
- คะแนน: ผ่าน 1 · ต้องติดตาม 0.5 · วิกฤต 0 หารด้วยจำนวนรายการ (สูตรเดียวกับ dashboard อ้างอิง) — เป็นการคัดกรองหลักฐาน ไม่ใช่การตัดสินความสอดคล้อง
- ผู้ตรวจสอบขึ้นไปกด "บันทึกผลครั้งนี้" เก็บประวัติ (`readiness_runs`) · ส่งออก CSV (Excel ภาษาไทย, กันสูตร) / JSON
- หน้าแดชบอร์ดแสดงการ์ดความพร้อม, DCR รออนุมัติ, CAR/DAR/PAR และรายการที่ต้องทำก่อน Audit 5 อันดับแรก

## การแจกจ่ายและรับทราบเอกสาร (ISO 9001:2015 ข้อ 7.5.3, 7.3, 7.2)
`api/src/acks.rs` · เมนู "การรับทราบเอกสาร" · แท็บ "การแจกจ่าย/รับทราบ" ในหน้าเอกสาร
- **รายชื่อแจกจ่าย** ต่อเอกสาร: แผนก / พนักงาน / บทบาท / ทุกคน — ค่าเริ่มต้น = แผนกเจ้าของเอกสาร, QM = ทุกคน (แก้โดยผู้ตรวจสอบขึ้นไป)
- **DCR มีผล → ส่งคำขอรับทราบ Rev. ใหม่อัตโนมัติ** ครบกำหนด 14 วัน · คำขอ Rev. เก่าที่ค้างถูกแทนที่ · ยกเลิกใช้ → คำขอค้างถูกแทนที่ · นำกลับมาใช้ → ส่งคำขอฉบับปัจจุบันอีกครั้ง
- ผู้ตรวจสอบขึ้นไปส่งคำขอฉบับปัจจุบันเองได้ (รายฉบับ หรือทีละหลายฉบับตามประเภท/แผนก) — คนที่มีคำขอแล้วไม่ถูกส่งซ้ำ
- **ผู้รับต้องเปิดอ่านฉบับนั้นก่อน** (ระบบบันทึกเวลาเปิด) แล้วลงนาม "อ่านและเข้าใจแล้ว" ด้วย PIN → บันทึกเข้า `training_log` เป็นหลักฐาน
- ภาพรวม: อัตรารับทราบของฉบับปัจจุบัน (ประวัติ Rev. เก่าไม่นับ), เลยกำหนด, ส่งออก CSV · เตรียม Audit มีรายการตรวจ "ผู้เกี่ยวข้องรับทราบเอกสารฉบับปัจจุบันตามกำหนด" · ทบทวนฝ่ายบริหาร หัวข้อทรัพยากรแสดงอัตรารับทราบ

## ตรวจติดตามคุณภาพภายใน (ISO 9001:2015 ข้อ 9.2)
`api/src/internalaudit.rs` · เมนู "ตรวจติดตามภายใน"
- **แผนประจำปี**: แต่ละการตรวจ = ข้อกำหนดที่ตรวจ + แผนก + หัวหน้า/ผู้ตรวจร่วม + ผู้รับการตรวจ + วันที่ · ตารางความครอบคลุมข้อ 4–10 ของปี (วางแผนโดยผู้ตรวจสอบขึ้นไป)
- **ความเป็นกลาง (9.2.2 b)**: ผู้ตรวจต้องขึ้นทะเบียน (admin ติ๊ก "ผู้ตรวจภายใน" ในหน้า ผู้ใช้และสิทธิ์) และต้องไม่อยู่แผนกที่ถูกตรวจ · ผู้ปิดการตรวจต้องไม่อยู่ในทีมผู้ตรวจ
- **เริ่มตรวจ** → สร้าง checklist จาก `data/clauses.json` พร้อมเอกสารอ้างอิงของแผนกที่ถูกตรวจ · ทีมผู้ตรวจบันทึกผล: สอดคล้อง / ข้อสังเกต (OFI) / NC เล็กน้อย / NC สำคัญ / ไม่เกี่ยวข้อง (ต้องมีหลักฐาน; OFI/NC ต้องมีข้อพบ) · เพิ่มข้อเองได้
- **NC → เปิด CAR** (แหล่งที่มา = ตรวจติดตามภายใน, อ้างอิงเลขที่การตรวจ, ผู้รับผิดชอบเริ่มต้น = ผู้รับการตรวจ, กำหนดเสร็จเริ่มต้น NC สำคัญ 14 วัน / เล็กน้อย 30 วัน)
- **ลงนามรายงาน** (หัวหน้าผู้ตรวจ + PIN + SHA-256) ได้เมื่อบันทึกผลครบและทุก NC มี CAR · **ปิด** โดยผู้อนุมัติที่ไม่อยู่ในทีม เมื่อ CAR ปิดครบ
- เตรียม Audit: แผนครอบคลุมทุกข้อ, มีรายงานที่ลงนามภายใน 12 เดือน (วิกฤตถ้าไม่มี), การตรวจเลยกำหนด · ทบทวนฝ่ายบริหาร: หัวข้อผลการตรวจดึงผลตรวจติดตามภายในมาเอง

## บังคับเปลี่ยน PIN
บัญชีที่ใช้ PIN ที่ผู้ดูแลตั้งให้ (หรือ PIN เริ่มต้นเดิม) มี `must_change_pin` — ใช้งานส่วนอื่นไม่ได้จนกว่าจะตั้ง PIN ของตนเอง · ห้าม PIN เลขซ้ำ/เรียง/ตามรหัสพนักงาน · ไม่มี PIN เริ่มต้นในโค้ด: ฐานข้อมูลใหม่สร้าง admin 900001 ด้วย env `ADMIN_PIN` หรือ PIN สุ่มที่แสดงในคอนโซลครั้งเดียว · พนักงานที่นำเข้าจากไฟล์ไม่มี PIN จนกว่าผู้ดูแลจะตั้งให้

## ทบทวนฝ่ายบริหาร (ISO 9001:2015 ข้อ 9.3 — ต่อยอดจาก management-review-dashboard)
`api/src/mreview.rs` · เมนู "ทบทวนฝ่ายบริหาร"
- **ข้อมูลนำเข้า 13 หัวข้อ (9.3.2 a–f)** ดึงจากระบบจริงเมื่อสร้าง/กด "ดึงข้อมูลจากระบบล่าสุด": งานจากการประชุมครั้งก่อน (ทุกฉบับแก้ไข), DCR และเอกสารยกเลิกใช้ (b), CAR/DAR/PAR (c4), ผลความพร้อมรับการตรวจ (c6), การอบรม FM-HR-008 (d) — หัวข้ออื่นบันทึกเองพร้อมหลักฐาน (รหัสเอกสาร/ลิงก์ http(s)) หรือระบุเหตุผลไม่เกี่ยวข้อง · การดึงซ้ำไม่ลบระเบียนที่บันทึกเอง
- ความครบถ้วน 17 รายการ (13 หัวข้อ + มติ + งาน + ผู้รับผิดชอบ + กำหนดเสร็จ) ต้องครบ 100% จึงส่งตรวจสอบได้ · ประเด็นที่ควรหยิบยก: KPI ไม่ถึงเป้า/แนวโน้มแย่ลง, สถานะวิกฤต, ไม่มีหลักฐาน, งานเลยกำหนด
- ขั้นตอน **ร่าง → รอตรวจสอบ → รออนุมัติ → ติดตามงาน → ปิด** ลงนามด้วยบัญชีพนักงาน + PIN ทุกขั้น (ไม่มีช่องพิมพ์ชื่อ) · ลายเซ็นเก็บ SHA-256 ของเนื้อหาที่ลงนาม และเก็บประวัติครบแม้ถูกตีกลับ
- **แยกหน้าที่**: ผู้จัดทำ ≠ ผู้ตรวจสอบ ≠ ผู้อนุมัติ ในการประชุมเดียวกัน · เจ้าของงานอัปเดตความคืบหน้า/หลักฐานของตน แต่ทวนสอบประสิทธิผลเองไม่ได้ · อนุมัติงบเฉพาะผู้อนุมัติ (แก้งบหลังอนุมัติ → รออนุมัติใหม่) · ปิดได้เมื่อทุกงานเสร็จ + ทวนสอบแล้ว (admin ได้รับยกเว้นกฎแยกหน้าที่ — ถูกบันทึกใน audit log)
- หลังอนุมัติรายละเอียดงานล็อก — แก้ด้วย **ฉบับแก้ไข (revision)** จากฉบับล่าสุดเท่านั้น: ฉบับเดิมเป็น "ถูกแทนที่" และงานที่ยังเปิดย้ายไปฉบับใหม่ (ไม่ซ้ำสองที่)
- บันทึกการประชุมพิมพ์/บันทึก PDF ได้ (ป้าย "ร่าง" ถ้ายังไม่อนุมัติ) · ส่งออก JSON ครบชุดพร้อม snapshot ที่อนุมัติ
- หน้าเตรียม Audit เพิ่มรายการตรวจ 9.3: มีการทบทวนที่อนุมัติภายใน 12 เดือน (วิกฤตถ้าไม่มี) และงานจากการทบทวนที่เลยกำหนด

## ผู้ใช้และสิทธิ์
เมนู "ผู้ใช้และสิทธิ์" (admin เท่านั้น): ค้นหา/กรองตามบทบาท, เปลี่ยนบทบาท/แผนก/ตำแหน่ง, เปิด-ปิดบัญชี (ปิดแล้วเซสชันใช้ไม่ได้ทันที), ตั้ง PIN ใหม่, ตารางสิทธิ์ตามบทบาท — ห้ามลดสิทธิ์/ปิด admin คนสุดท้าย · บทบาท: `viewer` อ่านอย่างเดียว · `preparer` จัดทำ · `reviewer` ตรวจสอบ/ทวนสอบ · `approver` อนุมัติ/ปิด · `admin` จัดการระบบ

## เวอร์ชันไฟล์ (ไม่ทับของเดิม)
- ทุกการแก้บนเว็บ/อัปโหลดไฟล์ใหม่ = **เวอร์ชันใหม่** ใน `data/storage/` (`<รหัส>__v<N>.<ext>`) พร้อมผู้แก้ไข วันเวลา ชื่อไฟล์ ขนาด SHA-256 และหมายเหตุ — เวอร์ชันเก่าเปิดดู/ดาวน์โหลดย้อนหลังได้เสมอ
- **เวอร์ชัน 1 (ต้นฉบับ) ถูกแช่แข็งเป็นสำเนาในคลังเวอร์ชัน** ตอนเริ่มระบบ/ครั้งแรกที่ใช้ — การแก้ไฟล์ในแฟ้ม `data/docs` (เช่นผ่าน OneDrive) หรือการซิงก์ฉบับล่าสุดลงแฟ้มจะไม่กระทบเวอร์ชันในระบบ
- ไฟล์ในแฟ้ม `data/docs` ถูกซิงก์เป็นฉบับล่าสุดเฉพาะเมื่อชนิดไฟล์ตรงกัน (อัปโหลด .pdf แทน .docx จะไม่เขียนทับ .docx)
- เอกสารในทะเบียนเปลี่ยนผ่าน DCR · ไฟล์ภาพรวมองค์กรที่ไม่อยู่ในทะเบียน แก้บนเว็บหรืออัปโหลดเวอร์ชันใหม่ได้โดยตรง (`/api/overview/save`, ประวัติ `/api/overview/history`)
- รายการทะเบียนและภาพรวมแสดง "vN · อัปเดตเมื่อ … โดย …"
- เวอร์ชัน 1 ที่ถูกเขียนทับไปก่อนมีการแช่แข็ง (`stored_name='LOST'`) แสดงว่าสูญหายพร้อมวิธีกู้ แทนการแสดงเนื้อหาผิดฉบับ

## CAR / DAR / PAR ครบวงจร (ISO 9001:2015 ข้อ 10.2)
`api/src/capa.rs` · **เปิด → กำลังดำเนินการ → รอทวนสอบ → ปิด** (หรือยกเลิกพร้อมเหตุผลโดยผู้ตรวจสอบขึ้นไป)
- ผู้เปิดใบ = ผู้ใช้ที่ login · ผู้รับผิดชอบเลือกจากรายชื่อพนักงาน · แหล่งที่มา (ตรวจติดตาม/ลูกค้า/กระบวนการ/ผู้ขาย/MR…) · อ้างอิงเอกสารในทะเบียนและเลขที่ DCR/MR
- ก่อนส่งทวนสอบต้องมี: CAR = การแก้ไขเฉพาะหน้า + สาเหตุที่แท้จริง (5 Why/ก้างปลา…) + การแก้ไขป้องกัน · PAR = สาเหตุที่อาจเกิด + มาตรการ · DAR = การดำเนินการ — ส่งทวนสอบลงนามด้วย PIN
- **ทวนสอบประสิทธิผล** โดยผู้ตรวจสอบขึ้นไปที่ไม่ใช่ผู้รับผิดชอบ (PIN + หลักฐาน): มีประสิทธิผล → ปิด · ไม่มีประสิทธิผล → กลับไปดำเนินการ
- ทุกขั้นเก็บใน `action_steps` และ `audit_log` · กันแก้ทับด้วย version · หน้าเตรียม Audit ตรวจว่าใบที่ปิดมีสาเหตุ/การดำเนินการ/ทวนสอบโดยผู้อื่นครบ

## บันทึกการใช้งาน (Audit trail)
เมนู "บันทึกการใช้งาน" (ผู้ตรวจสอบ ผู้อนุมัติ admin) — ค้นหาตามผู้ใช้ เลขที่ ประเภทการกระทำ และช่วงวันที่ (เวลาไทย) · ส่งออก CSV ให้ Auditor · แก้/ลบจากหน้าเว็บไม่ได้

## สำรองข้อมูลอัตโนมัติ
API สำรองฐานข้อมูลทั้งหมด (`pg_dump` ผ่าน Docker, container `BACKUP_PG_CONTAINER` ค่าเริ่มต้น `iso-postgres`) ตอนเริ่มระบบและทุก 24 ชม. ไปที่ `data/backups/db-YYYYMMDD.sql` + `forms-YYYYMMDD.json` เก็บ 30 วัน (ไฟล์ `pre-*.sql` ที่สำรองก่อน deploy ไม่ถูกลบ) — ควรคัดลอกโฟลเดอร์นี้ไปเก็บนอกเครื่องเป็นระยะ

## ความปลอดภัยของบัญชี
- ดาวน์โหลด/พรีวิวไฟล์ใช้คุกกี้ `iso_sid` (HttpOnly · SameSite=Strict · Path=/api · Secure เมื่อผ่าน HTTPS) — ไม่มี token ใน URL แล้ว · คุกกี้ใช้ได้เฉพาะคำขออ่าน (GET) การแก้ไขข้อมูลต้องมี Authorization header เสมอ (กัน CSRF)
- PIN เก็บเป็น **Argon2id + salt ต่อคน** — PIN ที่เก็บแบบเดิม (SHA-256) ยังใช้ได้ และถูกอัปเกรดเป็น Argon2 อัตโนมัติเมื่อ login/ลงนามสำเร็จครั้งถัดไป
- token ของ session / check-in สุ่มจาก CSPRNG ของระบบปฏิบัติการ (256 บิต)
- การนำเข้ารายชื่อตอนเริ่มระบบ (`data/eform/fmhr008-import.json`) เพิ่มเฉพาะพนักงานใหม่ — ไม่เขียนทับบทบาท/สถานะที่ผู้ดูแลแก้ในหน้า "ผู้ใช้และสิทธิ์"
